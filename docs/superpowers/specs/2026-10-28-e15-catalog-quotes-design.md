# E15 Catalog + Quote Design

**Status:** Accepted for implementation after independent builder review; story gates remain pending
**Date:** 2026-10-28
**Scope:** E15-S01 through E15-S08 only. E16 Document Engine is not included.

## Intent

Deliver a tenant-safe product catalog and quote lifecycle with deterministic arithmetic, policy-controlled human or automatic approval, immutable commercial versions, and a durable send intent. A quote being approved or queued for a document is not evidence that a PDF was generated or delivered.

## Goals

- Add a usable catalog and quote draft/API/UI backed by PostgreSQL.
- Keep prices, tax, discounts, approval, and send eligibility deterministic and auditable.
- Preserve tenant, entitlement, permission, and tenant-owned Organization Unit checks on every operation and reference.
- Make the S08 outbox event an honest, idempotent request boundary that E16 can consume later.
- Deliver each story in sequence with focused RED/GREEN tests, independent audit, documented gates, and a parent-owned commit/push before the next story.

## Non-goals

- Inventory, cost accounting, margin data sources, customer-organization subsystem, AI product matching, or generic scoped RBAC.
- PDF renderer, quote templates, generated-document storage, provider I/O, outbound-message creation, delivery callbacks, or `quote.sent`.
- Generic ActionRequest expansion. PRD §87 prefers approvals as specialized Action Requests, but E15 lacks the generic ActionRequest scope needed to safely extend that lifecycle. This ADR chooses a narrow quote approval record with a promotion path to the existing concept later.
- AppointmentService unification, physical product deletion, order processing, and customer acceptance/rejection flows.

## Existing contract and authority

- Use current `module.catalog`, `module.quotes`, and registered `catalog.read`, `catalog.manage`, `quotes.read`, `quotes.create`, `quotes.approve`, `quotes.send`, `tenant.settings.manage` keys. Never use role names as authority. No new permission key is needed.
- `module.catalog` gates catalog CRUD and catalog-backed item selection. `module.quotes` gates quote read/write/approval/send-intent operations. Creating a manual off-catalog line does not require `module.catalog`. Customer selection/resolution on draft writes and financial approval/send require `module.crm_lite` plus a current active same-tenant Contact; historical quote reads expose only quote-owned display snapshots under `module.quotes`. A send-intent command additionally requires `module.messaging.basic` and trusted active same-contact Conversation/Channel context. Draft/edit/approval do not require `module.documents`; actual document generation/delivery remains a future E16 capability.
- Global permission grants authorize tenant-wide access. The current RBAC resolver does not resolve OU-constrained grants; these fail closed. Do not claim generic OU-scoped RBAC. Validate every supplied Organization Unit, Contact, Product, Conversation, ChannelAccount, Quote, Version, and Intent against the authenticated tenant. A product with an OU may only be selected by a quote with that same OU; a product without an OU may be selected by any quote in the tenant.
- PRD §79 field names are older and less complete than backlog §18. Use the backlog's `organization_unit_id`, `discount_total`, `tax_total`, `approved_by_user_id`, timestamps, and `current_version`; do not add PRD `autonomous_decision` or nonexistent customer-organization/template/document foreign keys. PRD intent remains the same: quote/contact/items/totals/validity/terms/currency/salesperson/approval. Customer, OU and salesperson names are bounded owned display snapshots; do not accept unverified customer-organization IDs.
- ADR-022 is listed as approved in the PRD but has no file in the ADR directory. This design makes its existing “rules-controlled autonomy” principle executable without inventing an ADR-022 body.

## Data and catalog contract (S01–S02)

### Product

Tenant-owned `Product` fields: `id`, `tenantId`, nullable `organizationUnitId`, original `sku`, `normalizedSku`, `name`, nullable `description`, nullable `category`, `unit`, `price NUMERIC(19,4)`, uppercase three-letter `currency`, nullable opaque `taxCode`, nullable `taxRate NUMERIC(9,4)`, `active`, `isExceptional`, nullable bounded `customValues JSONB`, timestamps. Price is `0..999999999.9999`; SKU uniqueness is `(tenantId, normalizedSku)`. Archive sets `active=false`; no physical delete or inventory. Name uses the existing database-manager convention of 1–150 trimmed characters.

For S01, `normalizedSku` is Unicode NFKC, trimmed, then locale-independent uppercase; original trimmed spelling remains display data. Original and normalized SKU are each 1–64 UTF-16 code units, with no control characters; validate normalized expansion too. Name is 1–150 trimmed characters; description nullable ≤2000, category nullable ≤120, unit 1–32, taxCode nullable ≤64. `customValues` is null or a JSON object of at most 16 KiB UTF-8 after serialization and depth ≤8; reject arrays/primitives at root, invalid/cyclic JSON, excess depth/size, and prototype instructions. These are explicit E15 bounds.

Tax code is descriptive only. A null tax rate means “not configured” and blocks calculation; explicit `0` is the input for a non-taxed line. Do not infer a legal rate from country, code, or customer. A catalog product's current values never rewrite a quote line snapshot.

### Quote and lines

`Quote`: `id`, `tenantId`, required `organizationUnitId`, tenant-local `numberSequence BigInt`, unique tenant `number`, `contactId`, bounded customer display snapshots from existing `Contact.name`/`Contact.phoneNumber`, OU name snapshot from existing `OrganizationUnit.name`, salesperson display-name snapshot from authenticated creator's existing `User.displayName`, status, `autonomyLevelSnapshot`, currency and persisted `currencyPrecision`, nullable totals until calculated, nullable `validUntil`, terms, notes, creator type/id, nullable human approver type/id, approval time, sent/accepted/rejected times, `revision`, nullable `calculatedRevision`, nullable `calculationInputHash`, `currentVersion`, timestamps. Use backlog statuses `draft`, `pending_approval`, `approved`, `sent`, `accepted`, `rejected`, `expired`, `cancelled`; E15 does not add a Quote `pending_document` status or an expiry worker. Recorded history remains intact. Do not read Contact.customAttributes, user/tenant settings, or add an FK for customer-organization or future document/template models that do not exist.

`number` is `Q-` plus tenant-local `numberSequence` padded to at least six digits (`Q-000001` through `Q-9999999999`). Creation takes the tenant quote-number advisory lock and reads indexed `MAX(numberSequence)+1`; unique indexes cover `(tenantId, numberSequence)` and `(tenantId, number)`. No counter table/service. A failed transaction publishes no number. `currency` is explicit on draft creation, uppercased, and syntactically validated as three ASCII letters. Snapshot `currencyPrecision` once using installed Node `Intl.NumberFormat(..., {style:"currency"})` metadata; store and reuse it for all historic calculations. Do not claim this syntax check is an exhaustive ISO currency registry; do not convert currencies.

`QuoteItem`: quote id, line number, nullable product id, nullable SKU snapshot ≤64 code units, description 1–2000, positive decimal quantity, unit 1–32, `unitPrice`, discount kind/value, nullable opaque tax code, tax rate, nullable calculated gross/discount/net/tax/line total, nullable/object metadata ≤16 KiB UTF-8/depth 8. Manual off-catalog entries have `productId=null` and are exceptional. All persisted decimal values and HTTP/domain amounts are decimal strings. No JavaScript floating point. Product-bound unit price/SKU/description/tax fields are server-derived and cannot be overridden by request fields. Re-selecting a Product is the explicit refresh operation; an explicit authorized conversion to a manual line is required before a user can supply its commercial values. Unrelated quote metadata edits preserve all current item snapshots and prices.

Draft input contains no authoritative totals. S02 may store totals as null and `calculatedRevision=null`/`calculationInputHash=null`. S02 uses the tenant-policy advisory namespace for lock-order compatibility but neither queries nor creates QuotePolicy; it snapshots autonomy 0 and exposes no approval/send commands. S03 calculates on every draft create/update, stores each result and a canonical hash of the persisted calculation inputs, then sets `calculatedRevision=revision`. Approval/send rejects a quote unless `calculatedRevision === revision`, the stored-input hash matches, and all line tax inputs are configured.

## Calculation contract (S03)

- Product/quote unit price and shipping: maximum `999999999.9999`, at most four fractional digits. Quantity: `0 < quantity <= 999999.999`, at most three fractional digits. Tax/percent rates: `0..100`, at most four fractional digits; storage may use `NUMERIC(9,4)` but API and SQL constraints enforce ≤100. Fixed discount may be up to `999999999999999.9999` (`NUMERIC(19,4)` capacity), is additionally bounded by rounded line gross and quote currency precision. Aggregate amount: `NUMERIC(24,4)`. Quote line count: 1–200. Reject exponent notation, `NaN`, infinity, negative price/discount/shipping, excess precision, zero/negative quantity, and overflow.
- One tax mode: exclusive. For each line: `gross = HALF_UP(quantity × unitPrice, currencyPrecision)`; percent discount is `HALF_UP(gross × percent / 100, currencyPrecision)`; fixed discount is a per-line amount (not per unit), rounded/validated to currency precision; discount must be `0..gross`; `net = gross - discount`; `tax = HALF_UP(net × taxRate / 100, currencyPrecision)`; `lineTotal = net + tax`.
- Quote `subtotal` is sum of rounded line gross; `discountTotal` is sum of rounded line discounts; `taxTotal` is sum of rounded line tax; `shippingTotal` is an explicit nonnegative untaxed amount; `total = subtotal - discountTotal + taxTotal + shippingTotal`. No order-level discount. Fixed discount and shipping with excess currency precision are rejected, never silently trimmed. A fixed discount is a total amount for the line, not a per-unit amount.
- Use BigInt/scaled integer or rational arithmetic and return fixed-decimal strings at the persisted currency precision. Snapshot every input and result. Product/quote line currency must equal quote currency. A configured tax rate is a calculation input, not legal/tax advice.
- `calculationInputHash` is SHA-256 over canonical stored quote currency/precision, shipping, and ordered line calculation inputs (quantity, unit price, discount kind/value, tax rate). Formatting-equivalent normalized decimal inputs hash identically; a commercial input change changes the hash. S03 writes hash, totals, and `calculatedRevision` atomically.
- Reuse shared named constants for every input/storage bound in validators, Prisma/SQL constraints and UI validation; do not fork numeric literals across layers. Enforce request-only text/size limits before any write: quote terms ≤8000, notes ≤4000; entire normalized commercial draft header plus 1–200 lines ≤256 KiB UTF-8; no silent truncation. Reject unknown authority/totals/actor fields. Quote idempotency key length 1–128; approval reason/note ≤1000.
- `QuoteCommandReceipt` records only typed minimal outcome data (IDs, command/result, recorded revision/status/totals/decision/version/intent references), max 16 KiB; it does not duplicate full item arrays or mutable current views. Approval evidence snapshot ≤768 KiB, version snapshot ≤1 MiB, and public branding projection ≤64 KiB UTF-8. Validate before insert. UI formats exact decimal strings without `Number()`/`parseFloat()`, including aggregates beyond `Number.MAX_SAFE_INTEGER`.

## Quote policy and approvals (S04–S05)

### Policy

One tenant policy; no OU override in E15. Default is autonomy level 0 (manual), zero automatic approval/send, `requireStock=false`, `exceptionalProductRequiresApproval=true`, `allowSelfApproval=false`, and no configured ceilings. Policy read requires `module.quotes` + `quotes.read`; update requires `module.quotes` + both `tenant.settings.manage` and `quotes.approve`. Updates are audited and outboxed. Policy revision is monotonic; its SHA-256 hash covers normalized authorization fields plus revision, excluding actor/timestamps. A no-op write retains revision/hash; change-and-revert cannot resurrect an earlier hash. No policy reset/delete command.

Policy fields are `autonomyLevel` 0–3, nullable `maxAutoSendAmount` paired with required `maxAutoSendCurrency`, nullable `maxDiscountPercent`, nullable `minMarginPercent`, `requireStock`, `newCustomerRequiresApproval`, `exceptionalProductRequiresApproval`, `allowSelfApproval`, revision and timestamps. If autonomy 2 or 3 is selected, an explicit amount/currency ceiling is mandatory; quote currency must match it. No FX conversion. A missing/changed policy hash invalidates approval for send.

Only trusted database facts feed policy evaluation: prior tenant/contact quotes in `sent` or `accepted` status determine whether a customer is new; off-catalog or `Product.isExceptional` determines exceptional; configured `taxRate`/totals come from the frozen quote calculation. Never trust request booleans for stock, margin, or customer history. There is no stock or protected cost source in E15: `requireStock=true` or a configured `minMarginPercent` makes a quote ineligible for automatic approval and produces a structured human-review reason. A human approver may make and record an explicit review decision; that decision is not persisted as a stock/cost fact. Policy defaults to requiring human approval for exceptional products, including explicit manual/off-catalog conversions.

For each line, compare effective rounded line discount against rounded line gross and `maxDiscountPercent` by exact integer cross-multiplication. Do not calculate a floating-point percentage. A positive discount on zero gross is invalid; zero/zero is 0%. Null discount ceiling makes automatic eligibility fail closed. Autonomy 0 and 1 always route to human approval. Levels 2 and 3 use the same fail-closed deterministic eligibility gates; level 3 does not bypass limits. A new customer or exceptional item requires human approval when configured. Amount comparison is inclusive (`total <= ceiling`).

### Narrow approval lifecycle

S05 adds a `QuoteApproval` record for each request/decision rather than expanding generic ActionRequests. It stores tenant, quote, source revision, policy revision/hash, request actor/time, request state, nullable decision actor type/id/time, decision and structured reason code/note. Automatic approval uses `actorType=system_policy`, null actor id, and an explicit reason; it never impersonates a user. Manual approval requires `quotes.approve`. Self-approval is rejected unless the current policy explicitly enables it. Rejection is authenticated and recorded. Request and decisions atomically persist quote/approval state, AuditLog and Outbox.

`validUntil=null` means no automatic deadline. Non-null values are strict instants with offsets; after locks, sample current time and reject approval/version/send when `now >= validUntil`. No business timer or expiry transition is introduced. UI may derive an expired display/filter without changing recorded state; an editable unsent quote can receive a new validity and approval invalidation. A pending send intent must be cancelled before editing.

Segregation of duties records `QuoteCommercialContributor(tenantId, quoteId, userId, firstContributedAt)` for the creator and every authenticated actor who changes customer-facing/commercial draft content. E15 has no metadata-only quote edit endpoint; every accepted quote edit counts as a contribution. Default approver cannot be a recorded contributor. `allowSelfApproval=true` is the explicit tenant policy override and is included in policy and decision evidence.

Each quote mutation requires a stable tenant-scoped idempotency key and persists immutable `QuoteCommandReceipt(tenantId, key, commandType, actorUserId, resourceId, requestHash, recordedOutcome, createdAt)`. The normalized request hash binds command, actor, target resource, and normalized request. Same-key/same-hash replay returns the original outcome without rerunning the command even after quote edits or send cancellation; mismatch conflicts. Current authentication, module, permission, and tenant/resource guards run before replay. Keys cannot be reused for a different command, actor, or resource. Recorded outcome is labeled with its revision and is not returned as current mutable Quote state; UI fetches current separately.

All quote mutating commands obey this lock order: command-key advisory → tenant policy advisory (read/initialize effective policy under it) → tenant quote-number advisory (create only) → Quote row → needed Product/shared rows sorted by ID. All quote commands take the tenant policy mutex before reading policy; policy writers take it before create/update, including when creating the default. No command locks Quote before policy. Product CRUD never locks Quote. Quote creation uses indexed `MAX(numberSequence)+1` while holding the number lock; no counter service/table. Product selection/refresh locks needed Product rows only after Quote. Capture final clock after blocking locks and recheck current authority.

### Lifecycle matrix and cancellation (S02/S05/S07/S08)

- Create yields `draft`, revision 1; before S03 calculation, totals, `calculatedRevision` and `calculationInputHash` are null.
- Edit requires matching `expectedRevision`; permitted only from `draft`, `pending_approval`, `approved` or `rejected` when unsent. After S08 ships, it also requires zero pending intents. A real change returns to `draft`, increments revision, recalculates and clears current approval/version pointer while preserving append-only history. `sent`, `accepted`, `cancelled`, and recorded `expired` are terminal. A draft whose validity timestamp has elapsed may be edited to a new/null future deadline; effective expiry display does not rewrite recorded lifecycle status.
- Request approval is allowed from `draft`, `rejected`, and `approved` regardless of previous policy binding, or from `pending_approval` only when its current policy binding is stale. A fresh-key request while a current request is pending conflicts; same-key receipt replays. Request increments revision, recalculates, and either records pending human/assisted review or a final `system_policy` approval for an eligible level 2/3 path. It clears any prior current decision/version pointer while preserving version history; an immediately eligible system decision becomes the new current decision. System approval is not self-approval. A contributor may not decide manually unless policy enables self-approval. After S08 ships, any pending send intent blocks the request.
- Approve/reject only a current `pending_approval` at matching `expectedRevision` and policy binding; both increment revision, recalculate and persist decision bound to resulting revision. Changed policy requires new request/reauthorization first; no approval of an old request. Rejection is internal workflow state, never customer rejection or acceptance. Approval history is append-only.
- Request/approve/version/send deny at `now >= validUntil`; null has no deadline. Reject and quote cancel reduce authority and may execute after timestamp expiry, with normal actor/module/resource guards. There are no business timers.
- S05 adds idempotent `POST /api/v1/quotes/:id/cancel` under `quotes.create`, guarded by current tenant, authenticated actor, `module.quotes`, `quotes.create`, and tenant-owned Quote only; it does not require CRM/contact/send eligibility. It allows unsent `draft`, `pending_approval`, `approved` or `rejected`, transitions to `cancelled`, and increments revision once. If the Quote is still uncalculated or has missing tax inputs (S02 compatibility), cancellation remains allowed and leaves/sets all calculated totals/hash/`calculatedRevision` null; never invent zero totals. A new-key cancellation of already-cancelled quote returns `already_cancelled` without another business audit/outbox or revision bump; original-key replay returns its recorded result. Other terminal states deny. No reopen, clone or customer-acceptance workflow.
- S08 owns pending-intent freeze implementation: only when QuoteSendIntent exists, it patches S02 draft writes and S05 request/approve/reject/reauthorize/quote-cancel paths to deny while any intent for the Quote is `PENDING_DOCUMENT`. Before S08, S02/S05 must not query an absent table or invent a pending-intent shim. Canceling one intent unfreezes only if no other pending intent remains. Reads and idempotency receipt replays remain available; response exposes current pending-intent count separately from immutable recorded command outcome. Preserve partial uniqueness per tenant/version/channel to permit multiple channels; include channel A/B regression.
- All authority-only revisions recalculate from stored canonical inputs and atomically update totals, `calculatedRevision` and freshly derived hash. Storing `currentVersion` or creating/canceling send intents does not bump Quote revision. S07 snapshots on final approval; version reuse requires exact source revision, content hash, decision ID and policy binding; new approval evidence always has its own authority revision/version.

`quote.approved` and `quote.approval.requested` are outbox events. No expiry worker is introduced.

## UI (S06)

Create real Catalog and Quotes pages at the existing navigation destinations, replace current `href: null` entries, and use only the new API. Catalog: list/search/filter active, create/edit/archive, price/currency/tax inputs, explicit empty/loading/error/read-only/module states. S06 Quotes UI covers live list/draft/calculation/approval/policy only; it must not offer frozen-version history/preview or send-intent controls before those stories ship. Never render mock business data or enable an action the API does not support. Follow `UI_FLOWS.md` and `DESIGN.md` for responsive, keyboard, and existing component patterns.

## Immutable version and send intent (S07–S08)

`QuoteVersion` is tenant-owned and immutable with unique `(tenantId, quoteId, version)`; fields include source revision, SHA-256 commercial content hash, complete bounded commercial snapshot JSON, policy revision/hash, exact approval ID/decision evidence, validated current public `TenantTheme.config` projection, quote-owned customer name/phone, OU name, salesperson display name, and nullable unbound template/document markers only for future E16 linkage. Do not add nonexistent FK columns. No E15 code creates a template version, document row, PDF, or storage object. The snapshot has bounded line count/field sizes and decimal strings; changing Contact, OU, User, Products, policy or tenant branding cannot mutate it. Before reusing a version, compare source revision, commercial hash, exact approval decision ID and policy binding; never overwrite or resurrect stale evidence. Fresh approval evidence creates a new authority revision/version; receipt replay returns its recorded version.

S07 adds tenant-scoped `GET /api/v1/quotes/:id/versions` and `GET /api/v1/quotes/:id/versions/:version`, plus readonly frozen preview/history UI/model/tests in existing Quotes files. Render only immutable snapshot display fields; never join live CRM/product/user/theme data for an old version. Quote history exposes only owned quote snapshots under `module.quotes`.

S08 adds a tenant-owned `QuoteSendIntent` referencing exact QuoteVersion, Quote, Contact, same-contact Conversation, ChannelAccount, authenticated requester, idempotency key and canonical request hash. States: `PENDING_DOCUMENT` and `CANCELLED`. The queue command requires `module.quotes`, `quotes.send`, `module.crm_lite`, `module.messaging.basic`, approved current quote/version, unchanged policy hash/revision, calculated current revision, unexpired validity, active same-tenant Contact, and server-verified same-contact Conversation/Channel linkage. An explicitly authenticated human request is permitted; do not impose an AUTO-only rule. `contactId` is derived from the quote and not accepted as an authority from the request. No provider call, renderer, worker, BullMQ import, PDF or external dependency is added.

Intent insertion, AuditLog and `quote.send_requested` Outbox append commit atomically. Outbox payload carries only tenant/quote/version/intent/contact/conversation/channel identifiers and authenticated actor metadata; no free-form instructions or provider payload. The intent status remains `PENDING_DOCUMENT`; Quote remains `approved`, `sentAt=null`, and E15 does not emit `quote.sent`. Idempotency key plus same canonical request returns its original result; reuse with different input conflicts. A partial unique index permits at most one active pending intent per tenant/version/channel. Cancellation is an authority-reducing idempotent command: current authenticated user, active tenant, `module.quotes`, `quotes.send`, and owned Quote/Intent are required; current policy, validUntil, Contact/CRM, Channel, Conversation, messaging, and document eligibility are not. It must remain possible after those conditions are revoked and cannot send or revive anything. Record cancel audit/outbox and unfreeze source only when no other pending intent remains. A cancelled idempotency key remains consumed; a fresh request uses a fresh key. E16 later adds real typed document/template links and must recheck both `module.quotes` and `module.documents` and obtain actual trusted delivery evidence before sent state/event.

## Risks and review calls

1. `requireStock` and `minMarginPercent` have no inventory/cost truth in E15. The design intentionally blocks automatic paths and allows only an authenticated, structured human decision; confirm this policy treatment before S04/S05.
2. PRD §87 prefers ActionRequest specialization. The narrow `QuoteApproval` record is an explicit bounded alternative, not a claim that ActionRequest is unavailable forever. Review that the record can be promoted without data loss once its generic workflow is implemented.
3. PRD's older QUOTES→DOCUMENTS dependency is reconciled at capability level: quote drafting/approval and send-intent persistence require `module.quotes`; future actual rendering/delivery requires `module.documents`. This changes the meaning of the older coarse module matrix and needs PRD/backlog synchronization before release.
4. `Intl` metadata and three-letter syntax are intentionally not an ISO registry. Currency precision is persisted per quote so later runtime metadata changes cannot alter arithmetic.
5. Indexed tenant-local sequence (`Q-000001`), SKU normalization, `customValues` 16 KiB cap, per-line fixed-discount meaning, and exact effective line discount ratio are implementation-level choices that should be checked by the independent auditor.
