# ADR-0072 — E15 Catalog and Quote Contracts

**Status:** Accepted design; implementation tracked by story in STATUS
**Date:** 2026-10-28
**Decision owners:** Codex coordinator; independent architecture and scoped builder reviews completed

## Context

E15's backlog defines Catalog + Quote as eight stories but leaves most story acceptance criteria terse. The detailed backlog model is richer and more recent than the legacy PRD quote model. The PRD lists ADR-022 “Quote autonomy controlled by rules” as approved, but no ADR-022 record exists in `platform_docs/docs/adr/`. E15 also sits beside E16 Document Engine: a sent quote is normatively tied to an exact PDF, while E16 renderer, templates, storage and delivery are outside this authorization.

The existing permission and entitlement catalogs already provide `module.catalog`, `module.quotes`, `catalog.read`, `catalog.manage`, `quotes.read`, `quotes.create`, `quotes.approve`, `quotes.send`, and `tenant.settings.manage`. Current RBAC resolves global grants; OU-constrained grants fail closed. The product must remain tenant-safe and deterministic.

## Decision

### Product and quote model

1. Keep `Product` separate from `AppointmentService`. Model product tenant ownership, optional tenant-owned OU, normalized tenant-unique SKU, name/description/category, unit, nonnegative price, currency, optional tax code/rate, active/archive state, exceptional-product flag, bounded custom values, and timestamps. Do not add inventory or physical deletion. SKU original/normalized are 1–64 UTF-16 code units with no controls; normalize Unicode NFKC, trim, locale-independent uppercase, validate expansion, and preserve trimmed display spelling. Bounds: name 1–150, description ≤2000, category ≤120, unit 1–32, taxCode ≤64, customValues null/object ≤16 KiB UTF-8/depth 8, no arrays/primitives at root or prototype instructions. Product price is NUMERIC(19,4) up to 999999999.9999. Tax rate storage may use NUMERIC(9,4), while both API and SQL enforce 0..100. Product-bound quote snapshots are copied from the active Product. A user explicitly reselects a Product to refresh values or converts the line to manual to edit its commercial values; unrelated quote metadata edits preserve prior line prices/snapshots. Arbitrary product-bound price/tax/description overrides are rejected; explicit conversion to a visibly manual line is required before those values can change and triggers exceptional-product policy by default.
2. Use backlog §17–18 available field names for new schema: `organizationUnitId`, `discountTotal`, `taxTotal`, `approvedByUserId`, lifecycle timestamps, and `currentVersion`. Add E15 `revision`, nullable `calculatedRevision`, and nullable canonical `calculationInputHash` so calculated totals are bound to both the current revision and exact persisted inputs. Snapshot bounded customer name/phone, OU name, and authenticated creator's salesperson display name at draft create/edit and preserve on unrelated edits. Do not add unverified customer-organization ID, or FK columns for nonexistent template/generated-document models; no HTTP values are accepted for absent relations. Do not silently copy PRD §79's older `unit_id`, `customer_id`, `discount`, `tax`, `approval_status`, or `autonomous_decision` shape. Do not use live CRM projections for historical quote reads.
3. Keep canonical plural permission keys and existing module keys. Catalog operations require `module.catalog` and the corresponding `catalog.*` permission. Quote operations require `module.quotes` and the corresponding `quotes.*` permission. Contact selection/resolution and financial approval/send require `module.crm_lite` and an active same-tenant Contact. A quote with a catalog Product additionally requires `module.catalog`; manual off-catalog items do not. Channel send-intent requests require `module.messaging.basic` and trusted active same-contact Conversation/Channel context; an explicitly authenticated human send request is allowed and is not forced through an AUTO-only policy gate. Historical quote reads need only quote entitlement/permission and return owned snapshots. Drafting/approval does not require `module.documents`. The existing RBAC model is not extended to generic OU-scoped grants. Every reference is tenant-validated; a unit-bound Product must match the Quote unit; a global Product can be selected by any tenant unit.

### Money and calculation

1. API/domain money is decimal strings; commercial calculations use BigInt/scaled integer or rational operations, never JavaScript floating point. Store product price and fixed discount as `NUMERIC(19,4)` and calculated aggregate amounts as `NUMERIC(24,4)`. Tax rate storage may be `NUMERIC(9,4)` with SQL and API checks ≤100. Enforce max fixed discount 999999999999999.9999, additionally ≤ rounded line gross and currency precision; maximum product price/shipping 999999999.9999, quantity 999999.999, line count 1–200, quote draft total input ≤256 KiB UTF-8. Use reusable named bounds in validators, Prisma/SQL and UI. Full exact bounds are in the spec.
2. Quote currency is explicit, uppercase three-letter syntax. Resolve currency fraction precision once from the installed Node `Intl.NumberFormat` currency metadata and persist it on Quote; never recompute arithmetic precision for a historic QuoteVersion. This is not represented as an exhaustive ISO registry and there is no exchange conversion or mixed-currency line set.
3. Use one exclusive-tax mode. Round gross, discounts and tax per line at persisted currency precision using HALF_UP. Apply percentage or fixed per-line discount before tax; a fixed discount is an amount for the whole line, not per unit; reject discount greater than gross. Sum rounded line gross, discount and tax; add explicit nonnegative untaxed shipping. No order-level discount, tax-code lookup, or implied legal tax default. An unset rate blocks calculation; explicit zero is an input. Format UI amounts from exact decimal strings; do not coerce through JavaScript `Number` even for large totals.
4. Enforce `maxDiscountPercent` against each line's effective rounded discount / rounded gross using exact integer cross-multiplication. Positive discount on zero gross is invalid; zero discount/zero gross is 0%. Do not use floating computed ratios for policy authorization.
5. S02 can persist an uncalculated draft with nullable totals and calculation-input hash. S03 recalculates every draft mutation, stores a SHA-256 hash over canonical persisted currency/precision, shipping, and ordered line calculation inputs, binds the result to `calculatedRevision`, and quote approval/send fails closed when calculation is stale or incomplete. Authority-only revision changes reuse the same transaction-aware S03 recalculator over stored inputs, persisting totals, fresh input hash, and resulting revision marker together.
6. Bound quote terms ≤8000, notes ≤4000, line description 1–2000, line SKU nullable ≤64, unit 1–32, line metadata null/object ≤16 KiB UTF-8/depth 8. Reject unknown authority/totals/actor fields. Idempotency key 1–128, approval reason/note ≤1000. A minimal typed receipt outcome is ≤16 KiB and must not duplicate line arrays. Approval evidence ≤768 KiB, version snapshot ≤1 MiB, and public branding projection ≤64 KiB UTF-8; reject oversize before writes, never truncate.

### Numbering and deadline

1. Allocate tenant-local quote numbers `Q-000001` through `Q-9999999999` using an indexed tenant `MAX(numberSequence)+1` read under a tenant quote-number advisory lock. Store `numberSequence BigInt`; enforce unique `(tenantId, numberSequence)` and `(tenantId, number)`. Reject allocation once the next sequence exceeds 9,999,999,999. Do not add a counter service/table. A failed transaction does not publish a number.
2. `validUntil` is nullable; null means no automatic deadline. Non-null input is a strict instant including offset. Sample time only after blocking locks; at `now >= validUntil`, approval/version/send fails. E15 adds no expiry job or timer. UI may derive expired display state without rewriting lifecycle history. An unsent editable quote may receive a new deadline, invalidating prior approval.

### Autonomy and approval

1. Tenant policy defaults to autonomy 0/manual, automatic approvals disabled, self-approval disabled, stock requirement disabled, and exceptional-product approval required. Keep one tenant policy in E15; no OU policy precedence. S02 takes the stable tenant policy advisory lock namespace but does not query or create a QuotePolicy table and has no approval/send commands. S04 introduces QuotePolicy; absent row resolves to pure fixed revision-0 default/hash with no GET write, and explicit update creates/changes it under the same mutex. S05 reads effective policy under that mutex.
2. An automatic level 2/3 path requires an explicit `maxAutoSendAmount` and matching `maxAutoSendCurrency`. Both levels use the same deterministic eligibility gates; level 3 does not bypass a policy limit. Policy updates require `tenant.settings.manage` and `quotes.approve`; policy reads require `quotes.read`. Persist a monotonic policy revision and hash. A semantic no-op retains both; every semantic change increments revision, so changing and then reverting policy cannot revive old approval evidence.
3. Use tenant/contact quote history (`sent` or `accepted`) to identify a returning customer. Off-catalog line or explicit Product exceptional flag identifies exceptional product. Never trust request-supplied stock, margin, customer-history, or approval booleans. Without stock or protected cost data in E15, a required stock check or minimum margin prevents automatic approval and produces a structured human-review reason. An authenticated human decision can resolve the review and is audited as a decision, not stored as a stock/cost fact.
4. PRD §87 says an internal approval should preferably be a specialized ActionRequest. For this bounded scope, implement a narrow `QuoteApproval` record and approval-request/approve/reject operations. Do not expand generic ActionRequests or claim full workflow support. Preserve fields and events that permit later migration to an ActionRequest.
5. Record `QuoteCommercialContributor(tenantId, quoteId, userId, firstContributedAt)` for the creator and every authenticated actor who changes commercial/customer-facing draft content. No metadata-only quote edit API is part of E15. By default no recorded contributor may approve; `allowSelfApproval=true` is the explicit tenant policy exception and is copied into policy/decision evidence. Approval request, approve, reject, and reauthorization each increment `Quote.revision`; the resulting decision binds to the resulting revision. Version creation and send-intent/cancel bookkeeping do not increment it. If an authority-only revision changes no commercial input, still run canonical S03 recalculation from stored quote inputs within the caller's transaction and persist totals, calculation hash/input, and `calculatedRevision` together for the resulting revision; do not accept request totals or copy a stale calculation marker.
6. Every quote command, including policy mutations, has an immutable `QuoteCommandReceipt` keyed by tenant and a stable idempotency key, with command type, actor user, resource, normalized request hash, recorded outcome/revision and time. Same key/hash returns the original outcome without rerun; same key/different actor/command/resource/request conflicts. Current authentication, module, permission and resource checks still run before replay. Replays must distinguish the recorded result from current mutable Quote state.
7. All quote mutations acquire locks in this order: command-key advisory → tenant policy advisory (read/initialize effective default under lock) → quote-number advisory for create only → Quote row → needed Product/shared rows sorted by id. Policy writers use the same tenant mutex before create/update, including default creation. Product CRUD never locks Quote. No code path may lock Quote before policy or Product before Quote. Recheck current tenant/module/permission/resource authority and sample final time after blocking locks.
8. Approval commands lock and reread current Quote and policy, bind decision to Quote revision and policy hash, reject stale commands, enforce expiry, and are tenant/module/permission guarded. Self-approval is denied unless tenant policy explicitly enables it. Automatic decisions are attributed to `system_policy` with null user ID; never create a fake user actor.
9. Adopt this lifecycle matrix: create → `draft`, revision 1; edit only unsent `draft`/`pending_approval`/`approved`/`rejected` with matching expectedRevision → `draft`, revision+1, recalculate, clear current approval/version pointer and preserve history. Request allowed from `draft`/`rejected`/`approved` regardless of prior policy binding, or `pending_approval` only when policy binding is stale; duplicate fresh-key current pending request conflicts, same-key receipt replays. Request increments/recalculates, clears prior current decision/version pointer while preserving history, and produces pending human review or final eligible `system_policy` approval. Approve/reject only current pending_approval at matching revision+policy; both increment/recalculate and bind resulting revision. Changed policy requires fresh request first. Quote cancellation endpoint is S05 `POST /api/v1/quotes/:id/cancel` under `quotes.create`; unsent draft/pending_approval/approved/rejected → cancelled/revision+1. It requires tenant, actor, quotes.create, module.quotes, owned Quote but no CRM/contact/send eligibility. If the draft is uncalculated or has missing tax inputs, cancellation leaves calculated totals/hash/revision marker null rather than inventing zero; valid calculations may be rebound to resulting revision. New-key cancellation of already cancelled is an `already_cancelled` no-op without new business audit/outbox or revision; original key replays its recorded result. Sent/accepted/cancelled/recorded expired are terminal; no reopen/clone or customer acceptance flow. Reject and cancellation may still run after deadline; request/approve/version/send deny at `now >= validUntil`.
10. Once S08 adds `QuoteSendIntent`, it patches S02/S05 mutation paths so any `PENDING_DOCUMENT` intent freezes quote edits, approval requests/decisions/reauthorization and quote cancellation. Earlier stories must not query the absent table or add a shim. Canceling one channel unfreezes only when no other pending intent remains; partial uniqueness still permits intents on multiple channels. Read and receipt replay remain available; include current pending count separately from immutable recorded outcome. Send-intent creation/cancel and currentVersion pointer maintenance do not bump revision. All approval authority-only bumps recalculate stored canonical inputs and update totals, hash and calculatedRevision atomically.

### Command receipt resource identity

Clarification2026-10-29: `QuoteCommandReceipt.resourceId` is required and binds
the actual target resource. Quote commands use their Quote ID and a matching
non-null `quoteId`; tenant policy commands use the owning Tenant ID and null
`quoteId`. The Tenant is the stable resource of its single policy, including
the absent-row default. This is not a sentinel or a fabricated QuotePolicy FK.
S02 only implements quote commands; S04 later adds policy commands using the

### Version and send boundary

1. Create immutable tenant-owned `QuoteVersion` only after final approval. It contains source revision, complete bounded commercial JSON snapshot with decimal strings, policy revision/hash, exact approval ID/decision evidence, immutable customer name/phone, OU name, authenticated salesperson display snapshots, actual validated public tenant branding projection, and unbound nullable template/document markers only (no FK to nonexistent models). Before reusing an existing version, compare source revision, commercial hash, exact approval decision ID and policy binding; a matching content hash alone cannot reuse stale approval. New approval evidence gets a new authority revision/version. Version creation does not increment quote revision. E15 creates no template version, generated-document record, PDF, or storage object.
1a. S07 adds `GET /api/v1/quotes/:id/versions` and `GET /api/v1/quotes/:id/versions/:version`, plus read-only frozen preview/history UI and tests in existing Quotes files. Render only immutable snapshot fields, never live Contact/OU/User/Product/theme joins. Historical quote reads expose only owned snapshots under `module.quotes`.
2. S08 creates a durable `QuoteSendIntent`, not a sent quote. It references exact QuoteVersion, Quote, Contact, same-contact Conversation, ChannelAccount, authenticated requester, idempotency key and canonical request hash. It requires `module.quotes`/`quotes.send`, `module.crm_lite` with active same-tenant Contact, and `module.messaging.basic` with trusted active same-contact Conversation/Channel. Explicit human request is allowed independent of AUTO policy. It atomically persists AuditLog and a `quote.send_requested` Outbox event. No provider I/O, renderer, worker, BullMQ import, transport-specific capability, or external dependency is introduced.
3. While pending, intent status is `PENDING_DOCUMENT`; Quote remains `approved`, `sentAt` remains null, and E15 emits no `quote.sent`. Same key + same canonical input returns the original result; same key + different input conflicts. Permit at most one active pending intent per tenant/version/channel with a PostgreSQL partial unique index. Intent cancellation requires active tenant/current authenticated user, `module.quotes`, `quotes.send` and owned Quote/Intent only; it deliberately ignores validity, policy, Contact/Conversation/Channel state and CRM/messaging/documents entitlement revocation so a pending request can be canceled after those authorities change. It cannot send or revive. Cancelled keys remain consumed and a new user intent uses a new key.
4. Quote lifecycle remains the backlog's existing status set. `PENDING_DOCUMENT` is only the intent state. Actual rendering/delivery requires E16 and `module.documents`; only future trusted delivery evidence may set sent state/time and emit `quote.sent`.
5. Resolve the PRD's coarse QUOTES→DOCUMENTS dependency at capability level: core quote lifecycle and send-intent persistence require `module.quotes`; actual quote document rendering/delivery requires `module.quotes` plus `module.documents`. Update PRD/backlog dependency language before release. This accepted decision separates the domain foundation from E16 document delivery.

## Alternatives considered

- Leave rounding/tax/discount behavior undefined and let each UI/API path decide: rejected because results would not be deterministic or auditable.
- Use JavaScript number arithmetic: rejected because binary floating-point cannot satisfy exact commercial rounding.
- Make level 3 bypass thresholds or treat missing stock/cost as success: rejected because PRD ADR-022 and project rules require deterministic policy authority.
- Expand the complete generic ActionRequest engine for quote approval: rejected for this epic because it would enlarge scope and make E15 depend on unrelated workflow completion; a narrow approval record preserves the path to later specialization.
- Generate a placeholder PDF, call a messaging provider, or emit `quote.sent` when an outbox request is stored: rejected because it would misrepresent E16 or delivery evidence.
- Require `module.documents` for quote drafts: rejected because it would prevent a tenant from preparing and approving commercial quotes without the renderer; document operations themselves remain entitled separately.

## Consequences

- S03 gets exact deterministic goldens; taxes remain configured input data, not legal/tax advice.
- Null or unknown pricing facts fail closed for automatic approval. Tenants can still use manual approval with authenticated, structured review evidence; this records the decision and reason, not a fabricated stock or margin fact.
- Quotes with a currency outside the policy's automatic ceiling remain manual. A tenant cannot mix currencies in one quote.
- No user sees a quote as sent until a future E16 consumer and trusted delivery integration provide that state transition.
- The narrow approval record must have a migration path to specialized ActionRequest data; no fake generic ActionRequest rows are created.
- The SKU normalization algorithm, custom-value byte cap, bounded sequence allocation, max-discount evaluation, and currency metadata behavior are concrete E15 calls that independent review should challenge before implementation.

## Migration / rollback

Use additive, append-only Prisma migrations, one per story's schema boundary. For each schema story, validate/generate Prisma and compare clean-schema SDL plus ordered Git-HEAD baseline upgrade against the actual SQL; parent applies locally and verifies checksums before prepared PostgreSQL runs. Once applied, SQL is immutable; corrections append a new migration. Preserve and report any historical BOM clean-chain limitation honestly. Do not backfill fabricated customer, product, tax, policy, approval, document, or send data. S02 has no QuotePolicy schema. S04 absent policy reads return the pure manual revision-0 default/hash without row creation; explicit policy PUT creates or updates it. Rollback is forward-only for shared environments: disable E15 routes/module access and preserve tenant rows; do not drop quote history, versions, intents, audit, or outbox records.
